# 정확도 측정 상세

README 의 요약 수치가 어떤 조건에서 나왔는지, 무엇이 아직 불확실한지 적는다. 수치는 모두 `eval/` 결과 파일에서 옮겼다.

## 용어

| 말 | 뜻 |
|---|---|
| 정답 | 시나리오나 데이터셋에 붙어 있는 근본 원인 서비스(시뮬레이터는 배포가 원인인지까지) |
| 최근 배포 베이스라인 | 첫 경보 직전에 배포한 서비스를 원인으로 고른다 |
| 첫 경보 베이스라인 | 경보가 가장 먼저 울린 서비스를 원인으로 고른다 |
| z 점수 최대 베이스라인 | 장애 주입 전 기준 구간 대비 가장 크게 변한 지표(z 점수 최대)의 서비스를 고른다. 주입 시각을 코드에서 직접 쓴다 |
| `rank_anomalies` 1위 | 조사 시점 기준 최근 5분을 그 이전 기준 구간과 비교한 z 점수 순위의 1위. 표준편차가 기준 구간 평균의 5%보다 작으면 5%로 올려 쓴다(표준편차 하한) |
| 하이브리드 | `rank_anomalies` 순위를 후보로 받은 에이전트 |
| 실행 1·실행 2 | 같은 25건을 에이전트로 돌린 횟수 |
| 반복 1·반복 2 | RCAEval 이 장애 종류마다 5번씩 기록해 둔 데이터 중 몇 번째 기록인지 |

LLM 은 temperature 0 에서도 실행마다 결과가 달라진다. 시뮬레이터 25건을 두 번 돌렸을 때 4건의 정답 여부가 바뀌었다. 그래서 25건 기준 2~3건 차이는 개선이나 퇴보로 보지 않는다.

## 시뮬레이터 25건

시나리오 5개를 시드 5개로 돌린 25건이다. 원인 서비스와 배포 여부가 둘 다 맞아야 정답이다. 베이스라인은 같은 입력에 늘 같은 답을 내므로 한 번만 적는다.

| 시나리오 | 함정 | 에이전트 실행 1 | 에이전트 실행 2 | 최근 배포 | 첫 경보 |
|---|---|---|---|---|---|
| deploy-regression | 원인 배포 10초 전에 무관한 배포가 있음 | 5/5 | 5/5 | 5/5 | 5/5 |
| db-degradation | DB 가 배포 없이 느려지고, 5초 전 무관한 배포가 있음 | 4/5 | 5/5 | 0/5 | 5/5 |
| retry-storm | DB 가 회복된 뒤에도 재시도 폭주로 장애가 이어지고, 그 뒤 핫픽스 배포는 효과가 없음 | 5/5 | 5/5 | 0/5 | 5/5 |
| silent-db | 원인 DB 에 경보가 없고, 직전 무관한 배포가 있음 | 2/5 | 3/5 | 0/5 | 0/5 |
| hidden-deploy | 원인 서비스에 경보가 없고, 5초 뒤 무관한 배포가 있음 | 5/5 | 5/5 | 5/5 | 0/5 |
| **전체** | | **21/25** | **23/25** | 10/25 | 15/25 |

- 조건: 모델 `nemotron-3.5-lightning-30b-a3b`(무료), temperature 0. 평가는 시나리오 3분 전체 기록으로 조사한다. 화면과 MCP 의 조사는 누른 시점까지만 보지만, 이 표는 그 제한 없이 잰 값이다. 실행 2 기준 조사 1건에 도구를 평균 8.4회 부르고 39초 걸렸다
- 두 실행은 결론 형식이 다르다. 실행 1([`eb8872e`](https://github.com/BonhaengLee/signal-desk/blob/eb8872e/eval/nemotron-3.5-lightning-30b-a3b.json))은 근거를 문자열 하나로 받았고, 실행 2([`eval/nemotron-3.5-lightning-30b-a3b.json`](../eval/nemotron-3.5-lightning-30b-a3b.json))는 근거마다 도구 호출 번호를 받는다. 실행 2는 25건 모두 결론을 냈고, 그중 3건은 최대 도구 호출 수 10회를 다 썼다. 형식을 바꾼 직후 한 번 더 돌린 실행(19/25)은 결과 파일을 남기지 않아 표에서 뺐다
- 커밋된 두 결과 파일에는 정답 여부·도구 호출 수·소요 시간만 있다. 스키마 검증 실패로 결론을 돌려보낸 횟수도 남지 않았다. 지금 평가 코드는 건마다 트레이스·종료 사유·스키마 검증 실패 수와 코드 버전을 남기고, 코드 버전이 다른 이전 결과는 다시 쓰지 않는다
- 처음 만든 시나리오 3개만으로는 첫 경보 베이스라인도 15/15 를 맞혀 에이전트와 차이가 없었다. 그래서 원인 서비스에 경보가 없는 시나리오 2개를 추가했다
- 재현: `npm run eval -- 5 nemotron-3.5-lightning-30b-a3b 5000` (`.env.example` 참고). 같은 코드 버전으로 이미 끝난 건은 다시 돌리지 않는다

### 한계

- **같은 시각에 울린 경보의 순서가 원인을 흘린다.** 시뮬레이터는 같은 틱 안에서 의존 대상 서비스의 이벤트를 먼저 내보낸다. 첫 경보 베이스라인이 맞힌 15건 중 8건은 여러 서비스 경보가 같은 시각에 울렸는데 이 순서 덕에 원인을 고른 것이다. 동시 경보를 판정 불가로 치면 7/25 다. 에이전트가 받는 경보 목록도 같은 순서라 같은 단서를 받는다. 순서를 섞으면 에이전트 정답률을 다시 재야 해서 다음 재측정 때 함께 고친다
- **원인이 깊으면 중간에서 멈춘다.** silent-db 는 두 실행 모두 5건 중 2~3건만 맞혔다. 틀린 답은 원인 DB 바로 위 서비스(`payment-api`)나 직전에 배포한 서비스였다
- **근거가 적어도 원인을 하나 고른다.** 결론 도구에 "아직 판단할 근거 없음"이 없어서, 경보 직후처럼 기록이 적을 때 조사해도 서비스 하나를 낸다. 이 결론은 잠정 결론으로 보고 승인 단계에서 사람이 거른다
- **지시문이 시나리오에 유리할 수 있다.** 에이전트 지시문에 "증상 이후 배포는 원인이 아니다" 같은 문장이 있다. 함정을 아는 사람이 쓴 지시문이다. 그래서 공개 데이터셋으로도 쟀다(아래)

## 공개 데이터셋: RCAEval RE1-OB

[RCAEval](https://doi.org/10.5281/zenodo.14590730)(CC BY 4.0)의 RE1-OB 는 Online Boutique(서비스 11개)에 장애를 넣고 지표만 기록한 데이터다. 서비스 5개에 cpu·mem·disk·delay·loss 장애를 하나씩 넣은 25종을 종류마다 5번씩 기록해 두었다. 원인 서비스가 맞으면 정답이다.

원본에는 경보가 없어서, 지연·에러가 기준 구간 평균 + 3σ 와 기준 구간의 1.5배를 둘 다 넘으면 경보를 만들었다. 기준 구간을 장애 주입 1분 전까지로 잡았으므로 주입 시각을 아는 상태에서 잰 셈이다.

### 반복 1: 에이전트와 베이스라인

| 장애 종류 | 에이전트 | 첫 경보 | z 점수 최대 |
|---|---|---|---|
| cpu | 2/5 | 1/5 | 5/5 |
| delay | 4/5 | 3/5 | 5/5 |
| disk | 3/5 | 3/5 | 4/5 |
| loss | 3/5 | 0/5 | 3/5 |
| mem | 4/5 | 3/5 | 4/5 |
| **전체** | **16/25** | 10/25 | **21/25** |

- z 점수 최대 베이스라인이 에이전트보다 높다
- 에이전트가 틀린 9건은 대부분 증상이 보이는 위쪽 서비스(frontend, checkoutservice, cartservice)를 제출했다. cpu 장애는 지연이 거의 늘지 않아 경보가 없고, 에이전트가 지연 위주로 보다가 놓쳤다
- 둘이 맞힌 건이 다르다. z 점수 최대만 맞힌 건이 8건, 에이전트만 맞힌 건이 3건이다. z 점수 최대가 틀린 4건은 원인이 아닌 서비스(emailservice 2건, adservice, recommendationservice)의 지표가 더 크게 변한 경우였고, 그중 3건을 에이전트가 맞혔다. 둘 중 하나라도 맞힌 건은 24건이다
- 조건: 모델 `nemotron-3.5-lightning-30b-a3b`, 최대 도구 호출 수 15회, 도구 평균 6.2회. 근거를 문자열 하나로 받던 이전 결론 형식으로 쟀다(반복 2도 같다)
- 결과 파일: [`eval/rcaeval-RE1-OB-run1-nemotron-3.5-lightning-30b-a3b.json`](../eval/rcaeval-RE1-OB-run1-nemotron-3.5-lightning-30b-a3b.json). 재현하려면 데이터를 `data/external/rcaeval/RE1-OB` 에 받은 뒤 `npm run eval:rca -- 1` 을 실행한다

### 반복 2: 하이브리드

반복 1 에서 두 가지를 바꿨다. z 점수는 기준 구간에 거의 안 움직이던 지표가 조금만 변해도 수조까지 커졌다. 그래서 표준편차 하한(기준 구간 평균의 5%)을 두고, 조사 시점 기준 최근 5분을 비교하는 순위 도구 `rank_anomalies` 를 만들었다. 에이전트는 이 순위를 후보로 받아 경보·호출 관계·다른 지표로 확인하게 했다. 하한 5% 는 반복 1 을 보고 정했으므로 채점은 처음 보는 반복 2 데이터 25건으로 했다.

| 장애 종류 | 에이전트 단독 | 하이브리드 | `rank_anomalies` 1위 | z 점수 최대 | 첫 경보 |
|---|---|---|---|---|---|
| cpu | 1/5 | 2/5 | 5/5 | 5/5 | 0/5 |
| delay | 4/5 | 5/5 | 4/5 | 2/5 | 2/5 |
| disk | 2/5 | 4/5 | 5/5 | 4/5 | 2/5 |
| loss | 2/5 | 2/5 | 2/5 | 1/5 | 3/5 |
| mem | 3/5 | 4/5 | 4/5 | 2/5 | 1/5 |
| **전체** | 12/25 | 17/25 | **20/25** | 14/25 | 8/25 |

- 결론: 이 데이터에서는 통계 순위가 답이고, 에이전트는 순위 결과를 설명하는 역할이 맞다. 에이전트가 순위를 뒤집을 때는 사람이 승인하는 지금 구조를 유지한다
- 순위를 주면 에이전트가 12 → 17 로 올랐다. 17 과 20 의 차이는 실행마다 달라지는 범위 안이라 건별로 봤다. 하이브리드가 순위 1위와 다른 답을 낸 7건 중 맞은 건 2건(cartservice_delay, checkoutservice_mem)이고, 맞던 순위를 뒤집어 틀린 건 5건이다
- 뒤집은 5건은 cartservice 3건, checkoutservice 2건을 제출했다. adservice_cpu/2 는 adservice cpu 의 z 가 1075, 2위가 1.9 인데도 cartservice 경보를 근거로 삼았다. 그 경보는 장애 주입 40초 **전**에 울린 잡음이다
- 1·2위 점수 차가 크면 순위를 그대로 쓰는 임계값도 따져 봤다. 차이가 가장 큰 두 건(17만 배, 8천 배)에서 1위가 틀렸고, 반복 1 로 임계값 10배를 정해 반복 2 에 적용하면 20/25 로 순위 단독과 같다. 그래서 넣지 않았다
- **조사 시점에 따라 순위 정확도가 크게 떨어진다.** 위 표는 장애 주입 5분 뒤 시점이라, 순위 도구의 "최근 5분"이 주입 이후 구간과 정확히 겹치는 유리한 조건이다. 시점을 앞당기면 `rank_anomalies` 1위는 주입 1분 뒤 18/25, 30초 뒤 8/25 로 떨어진다(반복 2). z 점수 최대 베이스라인은 주입 시각을 코드에서 직접 써서 시점의 영향을 받지 않지만, 실제 운영에서는 쓸 수 없는 정보를 쓴다. 재현: `node scripts/rank-window.ts 1 2` (LLM 호출 없음)
- 조건: 반복 1 과 같은 모델·최대 도구 호출 수, 실행 1회. 50건에 약 90만 토큰(NVIDIA 무료 한도)을 썼다
- 결과 파일: [`eval/rcaeval-RE1-OB-run2-nemotron-3.5-lightning-30b-a3b.json`](../eval/rcaeval-RE1-OB-run2-nemotron-3.5-lightning-30b-a3b.json), [`…-hybrid.json`](../eval/rcaeval-RE1-OB-run2-nemotron-3.5-lightning-30b-a3b-hybrid.json). 재현: `npm run eval:rca -- 2 nemotron-3.5-lightning-30b-a3b 5000 Infinity hybrid`
