# ADR-0006: 녹화 재생 데모를 정적 사이트로 배포

- 상태: 채택
- 날짜: 2026-11-10

## 풀려는 문제

저장소를 보는 사람이 직접 눌러 볼 화면이 없다. 실행하려면 Node 24, 저장소 복제, LLM 키가 필요하다. 조사 화면의 핵심(에이전트가 근거를 대고 사람이 승인·거절)을 키 없이 보여 줄 방법이 필요하다.

## 후보

| 후보 | 내용 |
|---|---|
| A. 서버째 배포 | 서버 맥에 SSE 서버·조사 API·SQLite 를 띄우고 터널로 공개한다. 방문자가 실제 모델로 조사를 돌린다 |
| B. 정적 사이트 + GitHub Pages | 빌드할 때 시뮬레이터 이벤트를 JSON 으로 만들고, 실제 모델로 미리 돌린 조사 녹화를 재생한다. 승인·거절은 브라우저 안에서만 반영한다 |
| C. 정적 사이트 + Cloudflare Pages | B 와 같고 호스팅만 다르다 |

## 비교 근거

- A 는 방문할 때마다 LLM 호출이 9회 안팎 든다. 무료 키 한도가 방문자 수에 묶이고, 공개 엔드포인트라 남용을 막을 장치(인증·속도 제한)가 따로 필요하다. 서버 맥이 꺼지면 데모도 꺼진다
- B·C 는 서버가 없어 운영할 것이 없다. 데모 데이터는 200KB 다(이벤트 3개 시나리오 + 녹화 3건)
- B 는 CI 가 이미 GitHub Actions 에 있어 워크플로 하나만 더하면 되고, 새 계정·비밀값이 없다. C 는 API 토큰을 저장소 비밀값으로 넣어야 한다
- 공식 문서: https://docs.github.com/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages

## 고른 것과 이유

B. 데모의 목적은 "에이전트가 무엇을 근거로 어떤 결론을 냈고, 사람이 그걸 보고 어떻게 결정하는가"를 보여 주는 것이다. 녹화로도 그 목적을 채운다.

- 화면 코드는 그대로 두고 데이터 출처만 바꾼다. `src/web/demo.ts` 가 `subscribe` 와 같은 모양으로 재생해서, 훅은 `VITE_DEMO` 에 따라 어느 쪽을 쓸지만 고른다
- 이벤트 파일에는 시나리오 정의를 넣지 않는다. 정답(`rootCause`)이 화면 데이터에 실리지 않게 하려는 것이고, 테스트(`test/demo.test.ts`)가 확인한다
- 녹화는 감사 로그를 조치 제안까지만 자른다. 결정은 방문자가 한다
- 녹화는 시나리오 T+120초 시점에 조사를 누른 것과 같다(`DEMO_AT_SEC`). 세 시나리오 모두 첫 경보가 T+60~70 이고 retry-storm 의 함정(핫픽스 배포)이 T+100 이라 그 뒤 20초까지 본다. 재생이 그 시점 전이면 데모는 조사를 시작하지 않고 시점을 안내한다
- 처음 녹화는 시나리오 전체 기록(3분)을 본 조사였다. 화면이 T+00:10 이어도 결론이 나와 "미래를 본다"는 문제가 있어 시점까지만 보게 고치고 다시 녹화했다

## 버린 대안과 그 대안의 가장 강한 장점

- A: 방문자가 새 조사를 돌려 볼 수 있다. 녹화는 같은 결과만 보여 준다. 실제 동작을 보려면 저장소를 받아 키를 넣고 돌려야 한다
- C: 지역 캐시가 GitHub Pages 보다 넓다. 데모 크기에서는 차이가 작다

## 되돌리는 비용

작다. 배포는 `.github/workflows/pages.yml` 하나이고, 데모 모드는 `VITE_DEMO` 를 켠 빌드에서만 쓴다. A 로 바꾸려면 서버 쪽 인증·속도 제한을 먼저 만들어야 한다.
