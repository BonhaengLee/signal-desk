# ADR-0002: 이벤트 목록 가상화

- 상태: 채택
- 날짜: 2026-11-08

## 풀려는 문제

장애 중에는 이벤트가 초당 수십 건씩 들어와 목록이 수천~수만 줄로 늘어난다. 모든 줄을 DOM 으로 만들면 처음 그리기와 새 이벤트 추가가 느려져 화면이 멈춘다. 운영자는 장애 중에 이 화면을 계속 보고 있어야 한다.

## 후보

| 후보 | 내용 |
|---|---|
| A. 가상화 없음 | 모든 줄을 그린다. 줄 컴포넌트는 `memo` 로 감싸 바뀌지 않은 줄은 다시 그리지 않는다 |
| B. 직접 구현 | 스크롤 위치로 보이는 범위를 계산해 그 줄만 그린다 |
| C. TanStack Virtual (`@tanstack/react-virtual` 3.14.26, MIT) | B 를 라이브러리로. 범위 계산·overscan·크기 측정·스크롤 동기화를 제공 |

## 비교 근거 (실측)

측정 페이지 `/?bench&n=10000` (`src/web/Bench.tsx`). 프로덕션 빌드, cmux 내장 브라우저, 같은 `EventList` 컴포넌트에서 `virtual` 만 바꿔 잰다. 렌더를 `flushSync` 로 끝내고 레이아웃을 강제로 계산시킨 시점까지 잰다(페인트 제외). 처음 그리기는 5회, 1건 추가는 30회의 중앙값이다. 브라우저 타이머 정밀도 때문에 1ms 단위로 반올림된다.

| 1만 건 | 처음 그리기 | 1건 맨 위 추가 | DOM 줄 수 |
|---|---|---|---|
| A. 가상화 없음 | 2764ms | 2612ms | 10,000 |
| C. TanStack Virtual | 3ms | 4ms | 34 |

- A 에서 줄을 `memo` 로 감싸기 전후 1건 추가 시간은 2316ms → 2612ms 로 줄지 않았다. 바뀌지 않은 줄의 React 렌더를 건너뛰어도 빨라지지 않았으므로, 비용 대부분은 1만 개 DOM 의 레이아웃에서 나온다고 판단한다(맨 위에 줄이 끼면 아래 줄 전부의 위치가 다시 계산된다). 브라우저 성능 도구로 레이아웃 시간을 따로 잰 것은 아니다. 이 판단대로라면 React 쪽 최적화로는 부족하고 DOM 수 자체를 줄여야 한다
- B 는 이번에 측정하지 않았다. 원리는 C 와 같고, 같은 34줄 수준의 DOM 이 나올 것으로 예상하지만 확인하지 않았다

## 고른 것과 이유

C. 측정에서 처음 그리기와 1건 추가 모두 약 1000배 빨라졌고, 이 차이는 DOM 수에서 나온다는 것이 확인됐다. B 대비 C 를 고른 이유는 일정이다. 아래 "남은 문제"의 가변 높이·크기 측정을 C 가 이미 제공한다.

## 버린 대안과 그 대안의 가장 강한 장점

- **A. 가상화 없음**: 코드가 가장 단순하고, 브라우저 찾기(Cmd+F)와 스크린 리더가 모든 줄을 본다. 목록이 수백 줄을 넘지 않는다면 A 가 이긴다
- **B. 직접 구현**: 의존성이 없고 동작을 완전히 통제한다. 고정 높이·단일 목록처럼 요구가 좁고 오래 유지할 코드라면 B 가 이긴다

## 남은 문제

- **맨 위 삽입 시 보던 위치가 밀린다.** 최신 이벤트를 위에 붙이는 구조라, 아래쪽을 읽는 중에 새 이벤트가 들어오면 읽던 줄이 내려간다. 스크롤이 맨 위가 아닐 때 새 이벤트를 "N건 새로 옴" 표시로 모아 두는 방식을 검토한다
- **줄 높이를 고정했다.** 긴 메시지는 한 줄로 자르고 `title` 로 전체를 보여 준다. 여러 줄 표시가 필요해지면 C 의 `measureElement` 로 실제 높이를 잰다
- **접근성.** 스크린 리더는 그려진 34줄만 본다. `aria-rowcount`·`aria-rowindex` 를 붙이는 작업이 남아 있다

## 되돌리는 비용

`src/web/EventList.tsx` 한 파일 안에 갇혀 있다. 이 파일의 `useVirtualizer` 부분만 바꾸면 B 나 다른 라이브러리로 교체할 수 있고, 나머지 화면은 `events` 배열만 넘긴다.
