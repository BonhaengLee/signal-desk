# ADR-0001: 화면 프레임워크와 타입 검사 도구

- 상태: 채택
- 날짜: 2026-11-08

## 풀려는 문제

브라우저 화면이 필요하다. 화면은 SSE 서버(`src/server/sse.ts`, 순수 Node)에서 이벤트를 받아 목록·경보·에이전트 조사 결과를 그린다. 서버 쪽은 이미 따로 있으므로 화면 프레임워크가 서버 기능을 가질 필요는 없다. 지금까지 타입 검사는 저장소 밖에 임시로 설치한 TypeScript 로 돌렸는데, 다른 사람도 같은 검사를 돌릴 수 있도록 저장소에 들여야 한다.

## 후보

| 후보 | 내용 |
|---|---|
| A. 라이브러리 없이 | DOM API 로 직접 그린다 |
| B. Vite + React | 개발 서버와 번들러는 Vite, 화면은 React |
| C. Next.js (App Router) | 라우팅·서버 컴포넌트·서버 함수까지 포함한 프레임워크 |

## 비교 근거

- 이 화면의 상태는 이벤트 목록, 경보 목록, 연결 상태, 승인 대기 조치가 서로 얽혀 바뀐다. A 는 상태가 바뀔 때 어떤 DOM 을 고칠지 직접 관리해야 해서, 보여 주려는 핵심(스트림 처리·가상화·승인 UX)보다 갱신 코드가 커진다
- C 의 강점인 서버 컴포넌트와 서버 함수는 이 구조에서 쓸 곳이 적다. 데이터는 이미 별도 SSE 서버에서 오고, 화면은 처음부터 끝까지 브라우저에서 상태를 들고 있어야 한다. 서버와 클라이언트 경계를 나누는 비용만 생긴다
- B 는 정적 파일로 빌드되어 SSE 서버가 같이 내보낼 수 있다. 개발 중에는 Vite 프록시로 같은 출처에서 `/events` 를 부를 수 있다 (Vite 공식 문서 `server.proxy`: https://vite.dev/config/server-options#server-proxy)
- 라이선스: vite, @vitejs/plugin-react, react, react-dom, typescript 모두 MIT (npm 레지스트리 메타데이터로 확인)

## 고른 것과 이유

B. Vite + React, 타입 검사는 TypeScript(`tsc --noEmit`). 화면 상태를 선언적으로 다루면서 서버 구조를 바꾸지 않는다. 서버 코드는 지금처럼 Node 의 타입 제거 실행(`node file.ts`)으로 돌리고, TypeScript 는 검사에만 쓴다.

## 버린 대안과 그 대안의 가장 강한 장점

- **C. Next.js**: 프론트엔드 채용 공고에서 가장 자주 요구되고, 라우팅과 배포 관례가 정해져 있다. 페이지가 여러 개로 늘고 검색 노출이 필요해지거나, SSE 서버를 같은 프로세스로 합치려 할 때는 C 가 이긴다
- **A. 라이브러리 없이**: 의존성이 0 이고 렌더링 비용을 완전히 통제한다. 화면이 목록 하나뿐이라면 A 가 이긴다

## 되돌리는 비용

- React 컴포넌트는 Next.js 의 클라이언트 컴포넌트로 거의 그대로 옮길 수 있다. 바뀌는 곳은 진입점(`src/web/main.tsx`), `vite.config.ts`, 개발 프록시 설정이다
- 파서·스키마·시뮬레이터는 프레임워크와 무관한 순수 함수라 영향이 없다
