# ADR-0004: 조사 도구를 MCP 서버로 노출

- 상태: 채택
- 날짜: 2026-11-09

## 풀려는 문제

조사 도구(경보·배포·지표·로그 조회)가 에이전트 루프 안에서만 쓰인다. 사람이 Claude Code 같은 도구로 같은 장애를 직접 조사하거나, 다른 에이전트가 이 도구를 빌려 쓸 방법이 없다. 도구 정의를 두 벌 두면 에이전트가 보는 것과 사람이 보는 것이 갈라진다.

## 후보

| 후보 | 내용 |
|---|---|
| A. 노출 안 함 | 에이전트 전용으로 둔다 |
| B. HTTP API | `/tools/:name` 같은 엔드포인트를 직접 만든다 |
| C. MCP 직접 구현 | JSON-RPC 2.0 over stdio 로 `initialize`·`tools/list`·`tools/call` 만 손으로 구현 |
| D. 공식 SDK (`@modelcontextprotocol/sdk` 1.32.2, MIT) | 프로토콜 협상·전송·스키마 검증을 SDK 가 맡는다 |

## 비교 근거

- MCP 클라이언트(Claude Code, Codex 등)는 B 의 임의 HTTP API 를 도구로 인식하지 못한다. 붙이려면 클라이언트마다 어댑터가 필요하다
- C 는 의존성이 없지만 버전 협상·capabilities·알림·취소를 직접 맞춰야 한다. 사양이 바뀔 때마다 따라가야 한다
- D 를 넣자 lock 파일의 패키지가 73 → 168 개로 늘었다(SDK 가 HTTP 전송용 express·hono 를 함께 끌어온다). 이 프로젝트는 stdio 만 쓴다
- 공식 문서: https://modelcontextprotocol.io/docs/concepts/tools

## 고른 것과 이유

D. 사양 추적을 SDK 에 맡기고, 우리 코드는 도구 정의와 실행만 가진다.

- `McpServer.registerTool` 대신 저수준 `Server` 를 쓴다. `registerTool` 은 zod 스키마를 요구하는데, 에이전트가 이미 JSON Schema(`TOOL_SPECS`)로 도구를 정의하고 있다. 저수준 `Server` 는 JSON Schema 를 그대로 받아서 정의가 한 곳에 남는다. SDK 는 `Server` 에 "고급 용도에만" 쓰라는 deprecated 표시를 달아 두었다
- 원인 제출(`submit_root_cause`)은 MCP 에 넣지 않는다. 판단은 클라이언트 몫이고, 평가용 정답(`rootCause`)도 응답에 넣지 않는다
- 검증: 메모리 전송으로 붙인 클라이언트가 받은 결과가 에이전트가 받는 `runTool` 결과와 같은지 테스트(`test/mcp.test.ts`). stdio 로 실제 프로세스를 띄워 도구 목록·호출까지 확인

## 버린 대안과 그 대안의 가장 강한 장점

- **A. 노출 안 함**: 코드와 의존성이 가장 적다. 사람이 도구를 직접 쓸 일이 없다면 A 가 이긴다
- **B. HTTP API**: 브라우저 화면에서 같은 도구를 바로 부를 수 있다. MCP 클라이언트 연동이 필요 없고 화면 전용이라면 B 가 이긴다
- **C. 직접 구현**: 의존성 0, 패키지 95개를 안 늘린다. 도구 3~4개를 stdio 로만 오래 유지하고 사양 변화를 감수할 수 있다면 C 가 이긴다

## 되돌리는 비용

`src/mcp/server.ts` 한 파일과 `test/mcp.test.ts` 만 SDK 를 import 한다. 도구 정의·실행(`src/agent/tools.ts`)은 SDK 를 모른다. 파일 둘을 지우고 의존성을 빼면 된다. SDK 2.x 에서 저수준 `Server` 가 빠지면 `McpServer` 로 옮기면서 zod 스키마를 `TOOL_SPECS` 에서 생성하는 작업이 필요하다.
